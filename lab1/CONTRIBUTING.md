# Участие в разработке

Спасибо, что хотите внести вклад в этот проект! Это репозиторий лабораторных работ по курсу «Системное программное обеспечение». Пожалуйста, прочитайте этот документ целиком, прежде чем предлагать изменения.

## Главное правило: код пишется без агентных ИИ

Весь код в этом репозитории должен быть написан человеком самостоятельно, вручную. Использование **агентных ИИ-инструментов** (автономных агентов генерации кода: Claude Code, Cursor, Codex, Copilot-агенты и любых аналогичных систем) для написания кода **запрещено**.

Разрешённые исключения — только для этих файлов и правок:

- `README.md`;
- `CONTRIBUTING.md` (этот файл);
- лицензионные правки в коде — например, SPDX-заголовки с авторством и лицензией.

Цель лабораторных работ — понять, как устроены операционные системы и системное программирование: события, процессы, IPC, мониторинг. Сгенерированный код этой цели не достигает, поэтому он не принимается. Мы открыто декларируем: `README.md` и `CONTRIBUTING.md` могли быть созданы с помощью ИИ — это разрешено. Честность важнее результата.

## Ревью и проверка понимания кода

Ментейнер проекта — **Magomed Gadzhiumarov**.

Каждый запрос на слияние (pull request) проходит ревью. В ходе ревью ментейнер проверяет, что автор **понимает** отправленный им код:

- просит объяснить, как и почему код работает;
- задаёт вопросы по конкретным решениям (например: почему здесь `termios`, что произойдёт при ошибке, где происходит системный вызов);
- может попросить что-то исправить или продемонстрировать работу программы.

Если автор не может продемонстрировать понимание своего кода, **запрос на слияние принудительно закрывается** без объединения. Это правило действует для всех без исключений и является осознанной политикой проекта.

## Как предложить изменение

1. **Issue.** Для крупных изменений (новый функционал, заметный рефакторинг) сначала откройте issue и опишите, что и зачем вы хотите сделать.
2. **Ветка.** Форкните репозиторий и создайте ветку с говорящим именем: `feature/<краткое-имя>` или `fix/<краткое-имя>`.
3. **Один PR — одна задача.** Маленькие, сфокусированные запросы на слияние рассматриваются быстрее.
4. **Проверьте локально.** Перед отправкой убедитесь, что проект собирается и программа работает (команды ниже), а код отформатирован.
5. **Pull request.** Опишите: что сделано, зачем, как это проверить. Сошлитесь на связанный issue.

## Требования к коду

- Язык — C++20 (GCC 13+ / Clang 17+). Целевая платформа — Linux (POSIX: `termios`, `/proc`, FIFO); варианты для Windows — по заданию лабораторной.
- Соблюдайте стиль репозитория: форматирование через `clang-format` с файлом `.clang-format` (стиль KDE/ECM):

  ```bash
  clang-format -i program_a/*.cpp program_a/*.h program_b/*.cpp program_c/*.cpp
  ```

- Сборка должна проходить без предупреждений компилятора; не подавляйте предупреждения без причины.
- Обрабатывайте ошибки: программа не должна падать при неверных аргументах, недоступном FIFO, нехватке памяти и т. п.
- Утечек памяти и выходов за границы массивов быть не должно; по возможности проверяйте под санитайзерами (`-fsanitize=address,undefined`).
- Комментарии на русском допустимы; имена сущностей — на английском, осмысленные.
- Не добавляйте сторонние библиотеки без обсуждения в issue.

## Коммиты

- Сообщения коммитов — осмысленные, на русском или английском. Рекомендуется формат [Conventional Commits](https://www.conventionalcommits.org/ru/): `feat: ...`, `fix: ...`, `docs: ...`, `refactor: ...`.
- Подписывайте коммиты `git commit -s` (Developer Certificate of Origin): подпись `Signed-off-by` подтверждает, что код написан вами лично и может распространяться под лицензией проекта.

## Сборка и проверка

```bash
cmake --preset gcc-debug        # конфигурация (GCC + Ninja)
cmake --build out/gcc-debug     # сборка

./out/gcc-debug/bin/program_a --color green   # запуск из каталога lab1 (лог: program_a.log)
```

Автотесты (`ctest`) появятся вместе с развитием лабораторных; после их добавления запросы на слияние без прохождения тестов рассматриваться не будут.
