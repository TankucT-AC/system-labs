# Лабораторная работа №1 — взаимодействие программ: события, запуск процессов, IPC и мониторинг

Курс «Системное программное обеспечение», 2026 год. Вариант 3 — **изменение цвета фона**.

Репозиторий содержит три программы (A, B, C), которые по заданию работают в связке: одна рисует изображение на экране и меняет его при нажатии клавиш, вторая запускает её с нужными параметрами и отправляет ей команды, третья следит за работой первой, ведёт собственный лог и «инжектирует» дополнительные команды. ## Компоненты

### Программа A — `program_a`

Интерактивное консольное приложение: меняет цвет фона терминала по нажатию клавиш и по командам из именованного канала (FIFO), ведёт лог событий. Начальный цвет задаётся параметром командной строки; если параметр не передан, используется значение по умолчанию. Команды из FIFO обрабатываются так же, как нажатия клавиш.

**Параметры командной строки**

| Аргумент         | Описание                                                        | По умолчанию |
| ---------------- | --------------------------------------------------------------- | ------------ |
| `--color <name>` | начальный цвет фона: `black`, `red`, `green`, `yellow`, `blue`  | `black`      |

**Управление с клавиатуры**

| Клавиша  | Действие                                                       |
| -------- | -------------------------------------------------------------- |
| `d`      | фон — чёрный                                                   |
| `r`      | фон — красный                                                  |
| `g`      | фон — зелёный                                                  |
| `y`      | фон — жёлтый                                                   |
| `b`      | фон — синий                                                    |
| `q`, `Q` | выход: в лог пишется `exit`, цвет терминала восстанавливается  |

**Внутреннее устройство**

- терминал переводится в неканонический режим через `termios` (`~ICANON`, `~ECHO`), символы читаются по одному;
- цвет фона задаётся ANSI/OSC-последовательностью `\033]11;#RRGGBB` (требуется современный эмулятор терминала с поддержкой OSC 11); при выходе посылается `\033]111` — возврат цвета терминала по умолчанию;
- смена цвета вызывается из двух потоков (главный цикл и поток FIFO), поэтому `Terminal::updateTerminalColor()` защищён мьютексом;
- в фоновом потоке открывается FIFO `/tmp/program_a_fifo` (неблокирующее чтение, повтор `open` при `EINTR`) и через `poll` ожидаются команды; команда `key=<символ>` обрабатывается как нажатие клавиши; при обрыве связи с писателем канала поток не завершается — программа ждёт нового подключения;
- каждое обработанное событие дописывается в лог `program_a.log` в текущем каталоге (см. [Формат логов](#формат-логов)); при старте пишется строка `key=` — это применение начального цвета.

Статус: реализованы цикл событий, клавиши, смена цвета, разбор аргументов, лог, приём команд `key=` из FIFO и устойчивость к обрыву связи; команда `cmd=color:<имя>` — в планах.

### Программа B — `program_b`

Пульт управления программой A: подключается к каналу, запускает A и отправляет ей команды из другого терминала.

- при старте создаёт (если нужно) и открывает FIFO `/tmp/program_a_fifo` на запись; открытие блокирующее — если читателя нет, B ждёт его появления (поэтому B запускается после A);
- игнорирует `SIGPIPE`: если все читатели канала отключились, `write` возвращает `EPIPE`, B печатает сообщение и завершается;
- находит `program_a` рядом со своим исполняемым файлом (через `/proc/self/exe`) и запускает её в окне alacritty (`posix_spawn`); проверяет, что файл существует, и сообщает об ошибке запуска;
- следит за процессом A (`waitpid` с `WNOHANG`) и завершается с сообщением, если A умерла;
- переводит терминал в неканонический режим (`termios`, общий модуль Terminal), читает клавиши по одной и отправляет их в канал уже открытым дескриптором (команда `key=<символ>`);
- `q`/`Q` — выход (в A не отправляется).

По заданию также планируются: поля для ввода параметров A (в варианте 3 — цвет фона) и передача их при запуске, отправка команды `cmd=color:<имя>`.

Статус: подключение к FIFO, запуск A, слежение за процессом и отправка команд реализованы; поля ввода параметров — в планах.

### Программа C — `program_c`

Программа мониторинга программы A (сейчас реализована первая часть — поиск и проверка A):

- ищет в `/proc` процесс с именем `program_a`, сканируя `/proc/<pid>/comm`;
- читает `/proc/<pid>/cmdline` и пересобирает из него `argv`, чтобы проверить аргументы запуска A: они прогоняются через тот же парсер `--color`, что и в модуле `Terminal`; при неверных параметрах C сообщает об ошибке;
- завершается с кодом 1 и понятным сообщением, если A не найдена или `/proc` недоступен;
- проверка разовая: C не ждёт появления A, а сразу сообщает, что её нет.

В планах (по заданию): определять по логу `program_a.log`, какая клавиша была нажата и когда; писать собственный лог `program_c/program_c.log` со временем запуска и завершения A; «инжектировать» дополнительные команды в FIFO; корректно переживать ситуации «A ещё не запущена», «A уже завершилась», «лог пуст», «FIFO недоступен».

Статус: реализованы поиск A и проверка её аргументов запуска; мониторинг, собственный лог и инъекция — в разработке. Для Windows по заданию потребуется отдельный скрипт `program_c.au3` (AutoIt).

## Архитектура взаимодействия

Целевая схема взаимодействия (по заданию): запуск процесса, именованный канал (FIFO), файловые логи и мониторинг через `/proc`.

```text
program_b ── запуск с параметрами ──► program_a
program_b ── команды ──────────────┐
program_c ── инъекция ─────────────┴► FIFO /tmp/program_a_fifo ──► program_a
program_c ── мониторинг (/proc/<pid>) ────────────────────────────► program_a
program_a ── program_a.log ──────────────────────────────────────► program_c (чтение событий)
program_c ── program_c.log (время запуска и завершения A)
```

Сейчас работают: поиск A и проверка её аргументов в программе C, подключение B к каналу, запуск A из B (`posix_spawn` + alacritty), отправка клавиш из B в FIFO, приём команд `key=` и устойчивость к обрыву связи в программе A. Остались: передача параметров A из B, мониторинг и инъекция в программе C; актуальное состояние — в разделе [Статус реализации](#статус-реализации).

## Требования

- **Linux** — текущая реализация использует POSIX-механизмы (`termios`, FIFO) и `/proc`; варианты для Windows — по заданию в планах (Win32 API, AutoIt).
- **CMake ≥ 3.21** — из-за версии схемы `CMakePresets.json` (version 3).
- **Компилятор с C++20**: GCC 13+ или Clang 17+ (требуется `std::format`).
- **Ninja** — генератор для пресетов сборки.
- **alacritty** — эмулятор терминала, в котором программа B запускает A (путь `/usr/bin/alacritty` зашит в коде). Для ручного запуска A не требуется.
- Опционально: `clang-format` (форматирование), `clangd` (навигация по коду — `.clangd` уже указывает на `out/gcc-debug`).

## Сборка

Все команды выполняются из каталога `lab1`.

### Linux — через пресеты (рекомендуется)

```bash
# Debug-сборка (GCC + Ninja)
cmake --preset gcc-debug
cmake --build out/gcc-debug

# Release-сборка (Clang + Ninja)
cmake --preset clang-release
cmake --build out/clang-release
```

Сборка отдельной цели: `cmake --build out/gcc-debug --target program_a`.

После сборки исполняемые файлы лежат в `out/<preset>/bin/` (каталог задаётся через `CMAKE_RUNTIME_OUTPUT_DIRECTORY`).

### Linux — вручную

```bash
cmake -S . -B out/manual -DCMAKE_BUILD_TYPE=Debug
cmake --build out/manual
```

### Windows

Пока не поддерживается. По заданию для Windows планируются: оконный вариант программы A (Win32 API, обработка `WM_KEYDOWN`), `CreateProcess`/`WM_COPYDATA` в программе B, скрипт `program_c.au3` для программы C; сборка через CMake с MSVC или MinGW-w64.

## Запуск

### Программа A (ручной запуск)

Запускать из каталога `lab1`: лог `program_a.log` создаётся в текущем каталоге.

```bash
cd lab1
mkfifo /tmp/program_a_fifo 2>/dev/null   # канал должен существовать до старта A
./out/gcc-debug/bin/program_a                # фон по умолчанию (чёрный)
./out/gcc-debug/bin/program_a --color green  # старт с зелёным фоном
```

Нажимайте `d`/`r`/`g`/`y`/`b` для смены цвета фона, `q` — выход. Программа работает в цикле событий: ждёт событие (клавишу или команду из FIFO), обрабатывает, обновляет экран, снова ждёт. FIFO открывается один раз при запуске — если канал не существовал в этот момент, приём команд работать не будет. Если писатель канала отключится (например, B завершится), A продолжит работу и примет новое подключение.

### Программа B (подключается к каналу и запускает A)

Запускать из каталога `lab1`, после того как A уже работает.

```bash
cd lab1
mkfifo /tmp/program_a_fifo 2>/dev/null   # канал должен существовать до старта A
./out/gcc-debug/bin/program_a            # терминал 1: A открывает канал на чтение
./out/gcc-debug/bin/program_b            # терминал 2: B подключается к каналу
```

B открывает канал при старте, поэтому запускать его нужно **после A**: без читателя блокирующее `open` будет ждать. Подключившись, B находит `program_a` в своём каталоге (`out/gcc-debug/bin/`) и открывает её в окне alacritty (если A уже была запущена, в окне появится ещё один экземпляр A). Клавиши `d`/`r`/`g`/`y`/`b`, нажатые в B, уходят в канал и применяются программой A; `q`/`Q` — выход из B. Если A завершилась (например, `q` внутри A), B сообщит об этом и завершится; если читатели канала исчезли, B сообщит об ошибке записи и завершится.

### Программа C

```bash
cd lab1
./out/gcc-debug/bin/program_c
```

C — разовая проверка: находит `program_a` в `/proc` и проверяет аргументы её запуска. Если A не запущена, печатает `ERROR: program_a is not found` и возвращает код 1. Мониторинг и инъекция команд — в разработке; планируемый порядок взаимодействия — см. [Демонстрационный сценарий](#демонстрационный-сценарий).

## Формат логов

**`program_a.log`** (создаётся в текущем каталоге; при запуске из `lab1` — `lab1/program_a.log`) — по одной строке на событие:

```text
2026-10-23 20:46:19 key= 
2026-10-23 20:46:26 key=r
2026-10-23 20:46:27 exit
```

Формат строки: `ГГГГ-ММ-ДД ЧЧ:ММ:СС key=<клавиша>`. Строка `key=` (после знака равенства стоит пробел) пишется при старте — это применение начального цвета, когда клавиша ещё не нажата. При завершении программы дописывается строка `ГГГГ-ММ-ДД ЧЧ:ММ:СС exit`.

Клавиши, полученные через FIFO, обрабатываются и логируются так же, как нажатые локально, — по логу источник не отличается. Клавиши вне набора `d`/`r`/`g`/`y`/`b` игнорируются и в лог не попадают.

**`program_c/program_c.log`** — в разработке; будет содержать время запуска и завершения программы A.

## Протокол команд (FIFO)

Для управления программой A из других процессов используется именованный канал `/tmp/program_a_fifo`. Программа A держит его открытым (неблокирующее чтение в фоновом потоке, ожидание через `poll`); пришедшие команды обрабатываются так же, как нажатия клавиш.

Команды — текстовые, по одной на сообщение:

| Команда            | Действие                                                          | Статус          |
| ------------------ | ----------------------------------------------------------------- | --------------- |
| `key=<символ>`     | обрабатывается как нажатие клавиши (например, `key=b` — синий фон) | ✅ реализовано   |
| `cmd=color:<имя>`  | смена цвета по имени (например, `cmd=color:blue`)                  | ⏳ в планах      |

Пример отправки команды из оболочки (программа A должна быть запущена):

```bash
mkfifo /tmp/program_a_fifo 2>/dev/null
echo -n 'key=b' > /tmp/program_a_fifo
```

Канал должен существовать к моменту запуска A: программа открывает FIFO один раз при старте и не переоткрывает его (см. [Запуск](#запуск) — во всех сценариях канал создаётся заранее). Программа B создаёт канал при старте, если его нет, и открывает его на запись; открытие блокирующее — B ждёт читателя, поэтому запускать её нужно после A. Если читатели отключатся во время работы, запись вернёт `EPIPE` (SIGPIPE игнорируется), B сообщит об ошибке и завершится. Программа A, наоборот, переживает отключение писателя и ждёт новое подключение. Неизвестные команды и сообщения с неподдерживаемым форматом игнорируются.

## Демонстрационный сценарий

1. Запускается программа C — она наблюдает за появлением программы A.
2. Запускается программа B.
3. Из B запускается A с параметрами (например, `--color blue`).
4. B отправляет A команду через FIFO.
5. C логирует нажатия клавиш, время запуска и завершения, инжектирует дополнительную команду.
6. A завершается (`q`), C фиксирует завершение в `program_c.log`.

Сейчас выполнимы: проверка программой C, что A запущена и с корректными аргументами, запуск A из B (пока без передачи параметров), отправка команд через FIFO, завершение A и выход из B. Наблюдение за появлением/завершением A, лог `program_c.log` и инъекция (шаги 1, 5, 6), а также передача параметров A при запуске — в разработке.
